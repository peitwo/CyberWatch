## 三、数据库设计落地

### 3.1 结构变更

**0003**：`event` 表加一列

```sql
ALTER TABLE event ADD COLUMN deleted_at DATETIME;   -- 可空，NULL = 未归档
CREATE INDEX ix_event_deleted_at ON event (deleted_at);
```

**0004**：新增 `status_history` 表（离线 SQL 原文，`alembic upgrade 0003:0004 --sql`）

```sql
CREATE TABLE status_history (
    id INTEGER NOT NULL,
    event_id INTEGER NOT NULL,
    old_status VARCHAR(13) NOT NULL,
    new_status VARCHAR(13) NOT NULL,
    reason VARCHAR(1000) NOT NULL,
    action VARCHAR(50) NOT NULL,
    actor_id VARCHAR(64) NOT NULL,
    changed_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY(event_id) REFERENCES event (id)
);
CREATE INDEX ix_status_history_event_id ON status_history (event_id);
UPDATE alembic_version SET version_num='0004' WHERE alembic_version.version_num = '0003';
```

### 3.2 数据流（一次状态变更）

```
浏览器 PATCH /events/{id} {status, reason}
        │
        ▼
update_event()
  ├─ session.get(Event, id)───── 不存在 → 404
  ├─ event.deleted_at 非空？ ─── 是 → 409（已归档不可改）
  ├─ model_dump(exclude_unset=True) → 取出 reason（reason 不是表列，必须先 pop）
  ├─ status 有变 且 requires_status_reason(old,new) 且 reason 为空 → 422
  ├─ 构造 StatusHistory(old_status, new_status, reason, action=status_change)
  ├─ event.sqlmodel_update(data)  ← 事件本体
  ├─ session.add(event); session.add(history)
  └─ session.commit()   ← ②与③同一事务，要么同时成功要么同时回滚
```

归档（`DELETE`）同理：`deleted_at = now()` + 一条 `action=archive` 的审计，一次提交。

### 3.3 「只读审计」的落实

`status_history` **没有任何写入路由**：客户端只能 `GET`，不能 `POST/PATCH/PUT/DELETE`。测试 `test_no_route_allows_modifying_history` 遍历应用路由表与 `test_history_write_endpoints_do_not_exist` 直接打这些方法，确认全部 405/404。伪造 `actor_id` / `action` / `old_status` 也会被 `EventUpdate` 的 `extra="forbid"` 拒绝（`test_client_cannot_forge_audit_fields`）。

## 四、后端实现要点

1. **原因校验是后端权威闸门**。前端弹窗只是体验层；`requires_status_reason` 是唯一真相：
   - `investigating → resolved`：必填「解决原因」；
   - `resolved → open / investigating`：必填「重新打开原因」；
   - 其余方向：可选。
   前端绕过（直接 fetch PATCH 不带 reason）实测 **HTTP 422**（见第六节浏览器验收第 16 项）。

2. **单事务原子性**。状态修改与审计写入共用一个 `Session`、一次 `commit()`。`test_status_and_audit_roll_back_together` 用 `monkeypatch` 把 `StatusHistory` 指向一个不存在的 `event_id=999999`，触发 `IntegrityError`，断言**事件状态回滚**——证明确实是原子写入，而不是「先改状态再补历史」。
   > 之所以用 monkeypatch 制造异常，而**不是**靠超长 reason 触发：SQLite 不强制 `VARCHAR(n)` 长度，超长值能写进去，用它会得到一个「假红」。

3. **SQLite 外键真实生效**。`PRAGMA foreign_keys` 是按连接生效的开关，SQLite 默认关闭。`enable_sqlite_foreign_keys` 在引擎的 `connect` 事件里每次执行 `PRAGMA foreign_keys=ON`。`test_foreign_key_is_really_enforced` 直接插一条指向不存在事件的 `status_history`，断言抛 `IntegrityError`（若未开启则静默写入）。

4. **归档语义一致**。归档不物理删行 → `status_history.event_id` 外键**始终有效**（`test_archived_event_row_still_satisfies_foreign_key`）。归档后：`GET /events/{id}` → 404、`PATCH` → 409、`DELETE` 再来一次 → 404、`GET /events/{id}/history` → 200 且可读。

5. **`reason` 的字段边界**：`max_length=1000`；显式传 `null` → 422（`test_reason_explicit_null_returns_422`）；超长 → 422。

## 五、前端实现要点（保持粉色 Kawaii Pastel Pop，纯原生 JS，未引入 React）

- **操作列三按钮**：`☰ 详情` / `✎ 编辑` / `✕ 归档`。归档按钮文案由「删除」改为「归档」，确认弹窗写明「归档后会从普通列表隐藏，但事件本体与全部历史记录都会保留」。
- **事件详情时间线**：`GET /events/{id}/history` → 竖向时间线，每条显示 `旧状态 → 新状态`、原因原文、操作主体、动作、时间；归档记录以「已归档」药丸呈现。
- **XSS 安全**：所有用户可控文本（标题、描述、原因）一律走 `textContent` / `createElement`，绝不 `innerHTML`。用标题 `<img src=x onerror=window.__xss=1>` + 描述 `<script>window.__xss=2</script>` 实测：`window.__xss` 未定义、表格内 0 个 `img/script` 元素、文本原样展示。
- **原因输入**：编辑弹窗内按「原状态 → 目标状态」动态显隐原因框，并前置提示；`investigating→resolved` 显示「解决原因（必填）」，`resolved→open/investigating` 显示「重新打开原因（必填）」。
- **重开二次确认**：`resolved → open/investigating` 必须再经过一个独立弹窗、填写重开原因才真正提交；取消则状态不变。
- **`sendPatch` 统一提交**：只发 `title/severity/status/description`（+ 需要时的 `reason`），未提交字段由后端保持原值（局部更新语义）。
- **配色**：未改动 `dashboard.css` 的 `:root` 变量，新增样式全部沿用原粉色系。

### 9.2 验收脚本缺陷（非产品问题，已修）

1. **时间线方向断言写错**：`badges` 只收集两个状态药丸，箭头 `.timeline-arrow` 是独立元素，`join('')` 得到的是「待处理调查中」而非「待处理→调查中」。显示的值其实完全正确，是断言字符串写错。
2. **第二次重开未填编辑弹窗原因**：脚本在第二次点 `#edit-save` 前没有填 `#edit-form textarea[name="reason"]`，而编辑弹窗自身也有必填校验（`dashboard.js` 提交处理里会提前 `return`），于是二次确认弹窗根本没机会弹出 → `waitForSelector('#reopen-dialog[open]')` 超时。第一次尝试时脚本先填了原因所以能过。补上填值后正常。

> 说明：这两处都在**验收脚本**里，不是产品缺陷；产品行为经后端与前端双重校验均正确。
