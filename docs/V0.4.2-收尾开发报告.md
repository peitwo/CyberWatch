## 二、后端改动

### 为什么新增独立接口，而不是改 `/events/archived` 的响应结构

把列表接口改成 `{total, items}` 信封是常见做法，但它会**破坏已有契约**：
`tests/test_restore.py` 有 11 处、浏览器验收脚本有多处按「数组」消费该接口。
本轮要求「禁止顺带重构无关模块」「保留现有 129 项测试」，因此选择**只增不改**：

```
GET /events/archived/count   →   {"total": 157}
GET /events/archived?offset=&limit=  →   [ArchivedEventRead, ...]   （保持不变）
```

两者条件同源（都是 `deleted_at IS NOT NULL`），因此计数与列表永远一致。

### 改动明细（`app/main.py`，共 +30 行）

1. `from sqlmodel import ... func ...`（+1 处 import 修改）
2. `class ArchivedEventCount(SQLModel)` — 11 行
3. `count_archived_events()` 端点 — 19 行

### 路由顺序（易踩的坑）

`GET /events/archived/count` **必须声明在 `GET /events/{event_id}` 之前**。
若被动态路由抢先，"archived" 会被当 int 解析 → **422**，归档中心计数直接失效。
已加专门守卫用例 `test_count_route_is_not_shadowed_by_event_id_path` 钉死。

## 三、前端改动

### 状态（`static/dashboard.js`）

```js
const ARCHIVE_PAGE_SIZE = 50;
let archivedEvents   = [];                  // 当前窗口内已加载的归档事件
let archivedTotal    = 0;                   // 后端权威总数（「共 N 条」的 N）
let archiveWindowSize = ARCHIVE_PAGE_SIZE;  // 窗口目标条数：恢复后按它重取
let archiveLoading    = false;              // 并发闸门
let archivePendingWant = null;              // 在途期间的新请求，只保留最后一次意图
```

### 三个针对性措施（对应需求 4）

| 目标 | 做法 |
|---|---|
| 不遗漏 | offset 用**实际返回条数**推进（`offset += page.length`），而不是「本轮想要多少」；中途归档集合变化也不会跳页 |
| 不重复事件 | 追加时按 `id` 去重（`Set`），同一事件不会渲染两次 |
| 不重复请求 | ① 单次加载全程 `maxInFlight === 1`（串行）；② 加载期间再次触发只**记录意图**，跑完补一次，连点 N 次最多触发 2 次加载；③ 按钮在加载期间 `disabled` |

### 加载窗口算法

```
runArchiveLoad(want):
    total = GET /events/archived/count            # 权威总数
    goal  = min(want, total)
    从 offset=0 起按 50 条串行取页，直至凑够 goal 或服务端已无更多
    按 id 去重后整体替换窗口，重渲染

loadArchiveWindow(want):
    if 正在加载: 记下意图并返回           # 合并，不并发、不丢弃
    else: 执行；若期间有新意图，补跑一次
```

### 恢复后如何保证「列表 / 总数 / 分页位置」正确

恢复成功 → `reloadLists()` → 归档中心仍打开时按 `archiveWindowSize`（当前窗口目标）
从 offset 0 **整体重取**，并重新拉一次总数。因为每次都是从 0 重取，
**不会出现「中间挖洞后 offset 前移导致漏掉一条」**，也不会有重复。
窗口目标条数不变，因此用户之前加载到第几页、恢复后就还停在第几页。

### 其他

- `#archive-count`（入口徽章）现在显示**权威总数**，不再是「本页条数」。
- 全部渲染仍走 `textContent`；恶意标题 `<img src=x onerror=...>` 原样显示、不执行（已验）。
- 归档中心关闭时只拉一次 count 维持徽章准确（`want = 0`），不会顺带拉列表。

## 六、已知限制

1. **offset 分页的固有窗口**：加载过程中若有第三方并发归档/恢复，重取窗口仍会收敛到
   服务端当前集合（不会错行），但用户看到的行序可能整体前移一位。未做游标（cursor）分页
   ——本项目单用户本地使用，暂不需要。
2. **恢复后按窗口整体重取**：窗口为 150 条时一次恢复会重发 3 页请求（每次 50 条，串行）。
   换取的是「绝不出空洞」。数据量再上一个量级时应换成游标分页 + 增量剔除。
3. **归档中心无搜索 / 筛选 / 排序 / 跳页**：本轮只做「加载更多」顺序翻页，未做条件筛选。
4. **归档中心表格右侧仍会有横向滚动**：长标题会把表格撑到容器 `min-width` 之外，
   `.archive-scroll` 走**容器内横向滚动**（与主表格 `min-width:1000px` 同一设计）。
   实测（157 条含 100 字长标题）：表格 735px / 容器 696px，溢出 39px；
   容器 `scrollLeft` 拉到最右后「恢复」按钮完整可见且可点击
   （`elementFromPoint` 命中该按钮），**页面整页无横向溢出**。此为既有设计，本轮未改动。
5. **归档总数没有「快捷刷新」**：只在打开归档中心、恢复/归档动作、点「刷新」时更新；
   若在其他标签页改了数据，需手动刷新。
6. 未覆盖浏览器：仅验 Chrome；未验 Safari / Firefox / 真机；未验 320px 及以下。
7. `actor_id` 仍固定为 `local-dev`（无账号体系）；仅 SQLite 后端。
