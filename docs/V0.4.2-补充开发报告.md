## 二、后端实现要点

### 2.1 路由顺序（本轮最容易踩的坑）

`GET /events/archived` **必须声明在** `GET /events/{event_id}` **之前**。FastAPI 按声明顺序匹配，
若放反了，`archived` 会被当作 `event_id` 去解析 int，直接返回 **422** —— 归档中心入口会「莫名其妙打不开」。
代码里已写明注释，并加了专门的守卫用例：

```python
def test_archived_list_route_is_not_shadowed_by_event_id_path(client):
    assert client.get("/events/archived").status_code == 200   # 不是 422
```

### 2.2 恢复的关键行为

```
POST /events/{id}/restore
  ├─ session.get(Event, id) ─── 不存在 → 404
  ├─ event.deleted_at is None？ ── 是（含重复恢复）→ 409
  ├─ event.deleted_at = None            ← 只动这一个字段
  ├─ session.add(StatusHistory(action="restore", old==new==status))
  └─ session.commit()                   ← 二者同一事务
```

- **只清 `deleted_at`**：`status` / `severity` / `created_at` / `title` / `description` 一律不碰；
- **审计 old == new**：状态本身没变，靠 `action` 区分「恢复」语义（与 `archive` 同一约定）；
- **`GET /events/{id}/history` 不检查 `deleted_at`**：归档事件的历史必须仍可复查，这是审计不可篡改的前提。

## 三、前端实现要点

- **入口**：事件面板头新增 `<button id="archive-btn">🗄 归档中心 <span id="archive-count">N</span></button>`，
  计数随归档/恢复实时刷新（`loadArchived()` 统一维护）。
- **归档中心弹窗**：表格列 `ID / 事件名称 / 等级 / 状态 / 归档时间 / 操作`；每行只有 `☰ 详情` 与 `↺ 恢复`（归档事件不可编辑）。
- **复用详情弹窗**：归档事件点「详情」能打开同一套时间线弹窗；`renderDetailMeta` 在 `deleted_at` 存在时**多显示一行「归档时间」**。
- **恢复流程**：`↺ 恢复` → 确认弹窗（写明事件名）→ 取消则状态不变 / 确认则 `POST /restore` →
  归档列表**原地刷新**（该行消失）+ 普通列表 + 统计卡片一起刷新 + 归档中心内显示可见成功提示。
- **失败提示**：恢复失败时错误显示在确认弹窗内的 `#restore-error`（弹窗保持打开，便于重试）。
- **安全**：所有用户数据（含归档事件的标题、原因）仍走 `textContent`，全文无 `innerHTML`；未引入 React；未改 `:root`。

### 4.4 手机窄屏下的既有交互约束（如实说明）

主事件表 `min-width:1000px`、归档表 `min-width:620px`，都在 `.table-scroll{overflow:auto}` 内。
因此 **390px 下需要横向滚动容器**才能看到最右侧的「操作」列；页面本身不横向溢出。
这是数据表的常规处理方式（避免 7 列被压成逐字竖排），已在验收中显式验证「按钮可滚动触达」。

## 五、发现并修复的问题

### 5.1 真实问题（已修）

1. **矮屏下弹窗高于视口**。390×844 时编辑弹窗高 748px（占 89% 视口高），在更矮的手机（如 390×640）会被顶出屏幕、底部按钮点不到。
   修复：`dashboard.css` 增加 `dialog{max-height:92vh;overflow:auto}`。
   **验证**：390×640 下编辑弹窗由 748px → **589px**，按钮可见可点（该视口 24 项全绿）。
2. **归档表的表头选择器会让既有验收脚本误判**。归档中心新增了第二张 `<table>`，基线脚本里未限定的
   `$$eval('thead th', …)` 会**同时匹配两张表**（返回 14 个 th），导致「表头 7 列」误报失败。
   这是**测试脚本的脆弱选择器**，不是产品缺陷（主表仍是 7 列）。已把选择器限定为 `#events thead th`，基线恢复 31/31。

### 5.2 编写验收脚本时我自己引入的两处逻辑错误（非产品问题）

- 把「对**仍在归档态**的事件调用恢复」误当成「应返回 409」——实际上它**本该返回 200**（那正是恢复成功的场景）。
  正确做法是拿一条**从未归档**的活跃事件来测 409。
- 在归档中心弹窗仍打开时去点击主表格的「归档」按钮，被模态拦截指针事件而超时；需先关闭归档中心。

两处均已修正，产品行为在 pytest 与 Chrome 两侧均确认正确。
