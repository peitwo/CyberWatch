### 1.1 Argon2id 性能与产物实测（5 次取中位）

| 指标 | 实测 | 说明 |
|---|---|---|
| `hash_password` | **72.7 ms**（min 71.1 / max 91.7） | 单次哈希 |
| `verify_password`（正确口令） | **72.4 ms**（min 70.1 / max 73.8） | |
| `verify_password`（错误口令） | **72.2 ms** | 与正确口径差 0.2 ms → **时间对齐成立** |
| 哈希串长度 | **97 字符** | 列宽 `VARCHAR(255)`，余量 2.6 倍 |
| 哈希串前缀 | `$argon2id$v=19$m=65536,t=3,p=2$` | 参数：`time_cost=3, memory_cost=65536, parallelism=2, hash_len=32, salt_len=16` |
| `password_needs_rehash` | `False` | 当前参数即最新参数 |

**兼容性结论**：批准引入的 `argon2-cffi` 在本环境可用；`Type.ID`、`InvalidHashError`、`VerifyMismatchError` 均在 25.1.0 中存在，无 API 变更影响。

> 顺带的效果：72 ms 是**有意保留的成本**。它同时是"离线爆破变慢"的保障，也是"在线撞库每秒最多 ~14 次"的天然节流 —— 这也是 §5.3 里"账号锁定不能单独作为限流方案"的量化依据。

### 5.2 值得单独说的几条守卫

**① 双向路由核对**（`test_every_app_route_is_declared_in_route_policy`）
`ROUTE_POLICY`（21 条已实现）与 `app.routes` 必须**精确相等**：漏登记 → 红；表里有而路由不存在（幽灵条目）→ 也红。另有 `PLANNED_ROUTE_POLICY`（6 条 V0.5.2 的 `/users*`）由 `test_planned_routes_are_not_implemented_yet` 守着：一旦实现就必须搬进 `ROUTE_POLICY`，**新接口不可能靠"留在计划表里"绕过守卫**。

**② 行为级全量拒绝**（`test_every_protected_route_rejects_anonymous`）
对**每一条**需权限路由发真实匿名请求 → 断言 401 + `WWW-Authenticate: Cookie`；对每条 HTML 路由 → 断言 302 + `location` 以 `/login?next=` 开头。并断言实际检查条数 ≥ 受保护路由数（防止"策略表被清空 → 循环没跑 → 假绿"）。

**③ 结构级守卫挂载**（`test_every_permission_route_carries_a_real_guard_dependency`）
不只看行为，还直接读 `route.dependant.dependencies[*].call.__qualname__`，断言每条需权限路由上真有 `require.<locals>.dependency`。`test_session_provider_alone_is_not_a_guard` 反向确认 `get_session` **不在**守卫名单里 —— 否则 `dependencies=[Depends(get_session)]` 这种写法能骗过"有没有依赖"的检查。

**④ 架构与纪律守卫**（`test_architecture.py`）
AST 扫描 import 图（无环 + 层级方向 + `LAYERS` 无遗漏）、表模型只许在 `models.py`、`utcnow` 只有一个定义、`security.py` 无孤儿导出、测试源码不得覆盖非 session 依赖、前端无框架且配色令牌不变。

## 8. 过程中发现并修复的真实缺陷

> 这一节是本报告最重要的一节。V0.5.1 的价值不只是"加了认证"，而是**在加的过程中把上一版留下的隐患逐个照出来了**。

### 8.1 `0006` 迁移原方案在 SQLite 上**根本跑不通**（架构级）

**发现**：设计文档 §3.3 原稿写 `op.add_column("status_history", sa.Column("actor_user_id", sa.Integer(), sa.ForeignKey("app_user.id")))`。
**实测**：SQLite 方言直接抛 `NotImplementedError: No support for ALTER of constraints in SQLite dialect.`
**且文档自相矛盾**：§3.1 的 ER 图宣称"真实外键"，§3.3 的代码却根本没把外键渲染进 DDL。
**修复**：改用 `batch_alter_table(copy_from=..., recreate="always")`（SQLite 的 copy-and-move 重建表），且**所有约束必须显式命名**（否则 `ValueError: Constraint must have a name`）；`downgrade` 的 `copy_from` 必须用"升级后"的定义；离线 `--sql` 的 `output_buffer` 必须是 `io.StringIO`（不是 list）。
**验证**：4 轮 spike + 实测证据 A/B/C 写回文档 §3.3.1；备选 Plan B（独立关联表）保留在案。
**影响**：如果没做这一步，V0.5.2 会在"第一次真的执行迁移"时炸掉。V0.5.1 的 0005 是纯建表，绕开了这个坑；但坑本身已经填好。

### 8.2 测试夹具的双库耦合让 17 条既有用例在鉴权后必然 401

**发现**：`client` 与 `client_and_engine` 各自建了**一个独立临时库**。V0.4.2 没有鉴权，请求发到哪个库都能跑通，所以一直没暴露。
**现象**：V0.5 加上服务端会话后，`client_and_engine` 一执行就把 `app.dependency_overrides[get_session]` 换成库 B，而 `client` 是在库 A 登录的 → 会话在库 B 查不到 → **17 条用例全部 401**（`test_status_history.py` 14 条 + `test_restore.py` 3 条）。
**修复**：不是给测试打补丁，而是让两个 fixture **共享同一个 `app_stack`**（同一临时库 + 同一 `TestClient` + 同一 Cookie 罐）。141 条既有断言一行都不用改。
**顺带**：`conftest` 新增 `AppStack` + `test_architecture.py::test_conftest_redirects_database_before_importing_app`（AST 取行号，断言"改环境变量"一定早于"import app"—— 这条顺序一旦颠倒，测试会静默地连上真实库）。

### 8.3 `ROUTE_POLICY` 的"幽灵条目"会让双向核对长期为红

**发现**：`/users*`（V0.5.2 才实现）被提前塞进 `ROUTE_POLICY`，于是"表里有、路由表里没有"的检查必然失败。这类守卫一旦长期报红，**唯一出路就是被关掉** —— 那就等于没有守卫。
**修复**：拆成 `ROUTE_POLICY`（已实现，双向精确核对）与 `PLANNED_ROUTE_POLICY`（计划中，不得与已实现路由重叠）；新增 `test_planned_routes_are_not_implemented_yet` 保证"实现后必须搬家"，新接口无法靠留在计划表里逃避守卫。

### 8.4 `utcnow` 有两份定义

**发现**：`models.py` 与 `security.py` 各写了一份实现（当时内容相同）。两份"现在几点"迟早漂移（比如一边改成返回 naive），而会话过期判定依赖它。
**修复**：`security.py` 改为 `from app.models import utcnow` 重新导出（`models → security` 与分层一致，不构成回边）；新增 `test_utcnow_has_exactly_one_definition`，附带断言 `security.utcnow is models.utcnow`（否则 monkeypatch 时间注入会失效一半）。

### 8.5 【真浏览器挖出】登录页的错误提示被共享封装吃掉了

**发现**：`cwFetch` 统一把 **任何** 401 翻译成"会话已过期，正在跳转登录页"。但登录接口的 401 含义是"口令不对"。
**现象**（真浏览器实测）：输错口令后页面显示 `登录失败：未登录或会话已过期，正在跳转登录页` —— 后端的「用户名或密码错误」被盖掉了，密码框也没清空。
**危害**：既是误导用户，也把后端刻意做的防账号枚举文案白白浪费（那句统一文案是 T3 对策的一部分，被前端一句话抹掉）。
**修复**：`api.js` 新增 `skipAuthRedirect` 选项，登录请求传 `true`；`login.js` 加注释说明为什么。回归：`test_login_request_opts_out_of_the_shared_401_redirect`（静态）+ 浏览器验收 B2/B3。
**为什么单元测试抓不到**：这是纯前端 JS 逻辑，`TestClient` 不执行 JS。

### 8.6 【真浏览器挖出】退出登录后浏览器仍能从缓存渲染 dashboard

**发现**：`/dashboard` 返回 200 且带 `etag` / `last-modified`，但**没有 `Cache-Control`**。
**现象**：退出登录后重新访问 `/dashboard`，Chrome 直接从缓存渲染出 dashboard 骨架，**根本没有再问服务器**。随后页面发的 API 请求 401 并跳回登录页 —— 最终结果是对的，但"一个无会话的浏览器渲染出已认证页面"这件事本身不该发生。
**修复**：新增 `no_store()` 包装 `FileResponse`，`/dashboard` 与 `/login` 都返回 `Cache-Control: no-store`。
**为什么单元测试抓不到**：`TestClient` / `httpx` **不实现 HTTP 缓存**。这是本项目第一次出现"只有真浏览器能发现"的缺陷类别。
**回归**：`test_authenticated_pages_are_not_cacheable`（断言 200 响应带 no-store）。

### 8.7 【真浏览器挖出 / 衍生加固】302 跳转也没带 no-store

**发现**：H 组检查时发现匿名 `/dashboard` 的 302 上没有 `Cache-Control`（因为跳转由依赖抛出，走不到路由函数）。
**风险评估**：302 **不属于** RFC 9111 §4.2.2 里"可被启发式缓存"的状态码，所以严格说不是漏洞。
**仍然修复**：显式加 `no-store`，并**在测试里钉住它**。理由写在 `test_anonymous_dashboard_redirect_is_not_cacheable` 里：哪天有人把 302 改成 301，而 **301 是可被缓存的** —— 那会让"登录后永远被跳回登录页"变成一个极难排查的问题。宁可现在多一行。

### 8.8 锁定状态可通过 `Retry-After` 响应头枚举账号（复核阶段主动发现）

**发现**：设计文档 §2.6 / §6.1 写的是"锁定期间 401 + `Retry-After`"。实现后复核时意识到：这个头**只有存在的账号才会带** —— 不存在的用户名永远走 `user is None` 分支，不会有这个头。
**实证**（对本机服务连打 6 次）：

```
admin            -> [(401, None), (401, None), (401, None), (401, None), (401, None), (401, '899')]
ghost-account    -> [(401, None), (401, None), (401, None), (401, None), (401, None), (401, None)]
```

**危害**：只要求 5 次，就能靠"第 6 次有没有这个头"判断账号是否存在 —— 前面做的统一文案 + Argon2 时间对齐（T3/T4）全部作废。
**为什么之前没想到**：T3 的验收口径是"状态码 / 文案 / 耗时"三项，**漏了响应头**这一项。
**修复**：移除 `Retry-After`，剩余时间只写服务端日志（用 `describe_duration` 转成中文可读文本）。锁定事实只体现在 `locked_until` 字段与日志里，不体现在任何响应里。
**取舍**：合法用户被锁定时也只能看到"用户名或密码错误"，看不到"请等待 N 分钟"。这与"停用账号不提示已停用"是同一个取舍 —— **宁可少一点提示，也不给枚举留缝隙**。
**文档同步**：§2.6 加了实现期校正注，§6.1 的 T2/T3 行改为"连响应头也一致 / 锁定分支不得新增任何响应头"。
**回归**：`test_locked_account_is_indistinguishable_from_unknown_account` —— 逐个头比对锁定响应与未知用户响应，**并断言锁定确实发生了**（防止这条用例靠"压根没锁上"通过）。

### 8.9 两处死代码 + 一处重复实现

**发现**：`security.py` 的 `seconds_since` 与 `describe_duration` 从未被调用；而 `app/auth.py` 自己又写了一遍 `(now - last_seen).total_seconds()`。两份相对时间运算比一份更容易在边界条件上分叉。
**修复**：`auth.py` 改用 `seconds_since`（`None → +inf` 天然落进"已超时"分支，顺手少了一个 `is None` 分支）；`describe_duration` 真正用于日志文本并明确"不用于 HTTP 响应"；新增 `test_security_module_has_no_orphan_helpers` 静态扫描 `security.py` 的孤儿导出。
**顺带修掉**：`describe_duration` 的 `f"{minutes} 分钟" + f"{rest} 秒"` 拼接缺空格（"2 分钟5 秒"），已改为"2 分钟 5 秒"，并由 8 条参数化用例钉住。

### 8.10 验收脚本自身的 5 处缺陷（工具也要可信）

| 问题 | 原因 | 修法 |
|---|---|---|
| `origin` 永远为 `null` | 浏览器**禁止** JS 设置 `Origin` 头，页面内做不出真正的跨站请求 | 拆成 `pageFetch`（页面内，验同源/ Cookie/ JS 逻辑）与 `nodeFetch`（Node 内，可显式伪造 `Origin`，验后端来源校验） |
| `DELETE` 收到 `json` 参数报 `TypeError` | `httpx.Client.delete()` 不接受 `json` | 只有非 DELETE 才传 body |
| `cwFetch` 断言偶发 `Execution context was destroyed` | 401 → `location.assign` 的导航可能早于 `evaluate` 的 CDP 往返完成 | 先挂起 `waitForURL`，再触发请求，并容忍 evaluate 被打断 |
| 第二次执行必然失败 | 脚本自己在 D4/D5 新建事件，而 C2 断言列表**恰好** 3 行 | 改为 `>= 3`（那不是产品缺陷，是脚本自己的脆弱假设） |
| 3 条断言写错预期 | `next=/dashboard` 未做 URL 编码（本就无需编码）、`#login-notice` 在 next 就是 dashboard 时**故意**不显示、`#user-name` 显示的是显示名而非用户名 | 按**真实设计意图**修正断言，并给 A4 改用 `?next=/events` 以真正触发提示分支 |
