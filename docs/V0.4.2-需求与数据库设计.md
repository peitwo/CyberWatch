# CyberWatch V0.4.2 需求与数据库设计

> 状态：**评审意见已并入，待最终批准**。本轮只做需求与数据库设计，**未修改任何项目代码、未安装依赖、未碰真实库**。
> 前置条件（用户明确要求，保持不变）：V0.4.1 的真实数据库迁移与 Git 合并需**先完成**，之后才能进入 V0.4.2 编码。
> 本版（V2）按评审意见调整：① 删除改软删除（`deleted_at`）；② 外键启用 `PRAGMA foreign_keys=ON`；③ 详情入口改"详情按钮 + 时间线弹窗"；④ 回滚测试改用非 VARCHAR 长度限制的确定性手段。

## 0. 产品定位

面向**个人开发者、安全学习者和小型团队**的轻量级开源 SOC 平台。V0.4.2 是「事件生命周期」从"单字段状态"升级为"可追溯审计"的关键一步：为每一次状态切换留下**只追加、不可篡改**的历史记录，并把删除升级为**可恢复的归档**。

## 2. 关键设计决策（写给初学者，附理由）

### 决策一：为什么历史记录要"新表 + 追加"，而不是在 event 表里加列？

- 状态是**随事件变化**的"当前值"；历史是**随时间增长的"过去值"**。二者生命周期不同。
- 若把旧状态塞进 event 表（如 `previous_status`），一次只能记住"上一步"，无法回答"这个事件从创建到解决一共改过 5 次，每次都谁、何时、为什么"。
- 独立表天然是**追加日志**：一行一次变更，永不覆盖、永不删除（需求 8）。

### 决策二：`old_status` / `new_status` / `action` 用 `str` 还是 `Enum`？

- **存库用 `str`（`VARCHAR`）**，不用 `sa.Enum`。理由与 V0.4.1 的 `status` 一致：`sa.Enum` 在 SQLite 上会额外生成 `CHECK` 约束，而我们的值域统一由 **Pydantic `Enum` 在 API 边界把关**。
- 但**校验层**仍用 `Status` 枚举：`EventUpdate.status` 已经是 `Status | None`，非法值会在进模型时被 Pydantic 拒绝为 422，所以 `new_status` 落库前一定是合法三值之一，无需再在 DB 加 CHECK。
- `action` 同理：本轮只有 `status_change` 一种动作，用 `str` + `default="status_change"`，避免过度设计枚举；未来加动作类型时再升格。

### 决策三：`event_id` 外键 + 启用 `PRAGMA foreign_keys=ON`

探针实测结论（写 `%TEMP%` 临时库）：

- `Field(foreign_key="event.id")` 生成的 DDL 会带 `FOREIGN KEY(event_id) REFERENCES event (id)`，`PRAGMA foreign_key_list` 也能列出这条约束。
- 但 **SQLite 默认不强制外键**：约束是否生效取决于连接时是否执行 `PRAGMA foreign_keys=ON`，SQLModel 的 `create_engine` 默认**不打开**。

评审要求「`status_history.event_id` 保持有效的数据库外键关联」，因此本轮**启用外键强制**：

- 在 `create_engine` 上挂一个 `event` 监听器（`sqlalchemy.event.listens_for(engine, "connect")`），每次新建连接时执行 `PRAGMA foreign_keys=ON`。这是 SQLAlchemy 官方推荐的 SQLite 外键开启方式，对应用连接与 Alembic 迁移连接**都生效**（二者共用同一 `engine` 配置来源）。
- 配合软删除（决策四），`event_id` 永远指向**仍然存在**的 event 行，外键不会因删除事件而悬挂。

**兼容性与测试影响（需在编码阶段验证）**：

1. 启用外键后，`DELETE /events/{id}` 若仍做物理删除，会因 `status_history` 引用而失败（`FOREIGN KEY constraint failed`）。这正是本轮**把删除改为软删除**的直接原因之一——软删除不动 `event` 行，外键始终有效。
2. 现有测试（`test_events.py` 的删除用例、`test_status.py`、`test_migrations.py`）**必须逐条回归**：其中"删除后 `GET` 得 404"的断言语义会变为"归档后默认列表不可见、但仍可归档查看"——这类用例需同步调整，且不能改动 `test_events.py` 之外的既有 16 条（见 §8 边界说明）。
3. 迁移测试若在临时库上做 `upgrade → downgrade`，`downgrade` 删表顺序需先删 `status_history` 再删 `event`，否则外键会阻止删表。设计 §3.3 已明确 `downgrade()` 顺序。
4. 内存库（`:memory:`）同样支持 `PRAGMA foreign_keys`，测试不受额外影响。

> 若未来切 PostgreSQL，`foreign_key="event.id"` 语义原样生效，届时按需加索引/级联即可，模型不变。

### 决策四：删除改软删除（`deleted_at`），历史记录永远留存

评审要求「事件删除采用软删除，保留事件本体及历史记录」。设计：

- `event` 表新增列 `deleted_at DATETIME NULL`（默认 `NULL`）。`NULL` = 未归档，非 `NULL` = 已归档（记录归档时间戳）。
- `DELETE /events/{id}` 语义改为**归档**：不删行，只把 `deleted_at` 设为当前 UTC 时间；返回 204（或 200，编码时定）。
- **普通列表 `GET /events` 默认只返回 `deleted_at IS NULL` 的事件**（归档事件不显示）。本轮**不新增**"归档中心 / 恢复"接口（评审要求"未来增加"，见 §7 边界）。
- 归档是**软删除**，`event` 行仍在 → `status_history.event_id` 外键**始终有效**，彻底消除决策三中"删事件导致外键悬挂"的问题。
- `get_event` / `update_event` 对已归档事件的可见性：默认按"已归档事件仍可读（详情/历史可见）、但不可再编辑状态"处理；编码阶段按测试口径固化（见 §4.4）。
- 归档操作本身**也产生审计记录**（评审要求第 11 条），见 §4.4 与 §5.4。

### 决策五：事务原子性与回滚测试（不依赖 VARCHAR 长度限制）

评审明确指出：**不能靠 SQLite 的 VARCHAR 长度限制来触发失败**（因为 SQLite 对 `VARCHAR(n)` 的 `n` 不强制，超长字符串照样写进去，之前的回滚测试手段是无效的）。

原子性保证（不变）：

- 后端在**同一个 `Session` 里**完成：`get(Event)` → 校验 → 改 `event.status` → `session.add(history)` → **一次** `session.commit()`。
- 期间无任何中间 `commit`，SQLAlchemy 将全部变更纳入一个事务；任一步抛异常则整体回滚。

**修正后的回滚测试方案**（确定性，不依赖 DB 类型限制）：

1. **注入失败法**：用 `pytest` 的 `monkeypatch` 把历史写入这一步替换为**必然抛异常**的桩函数（例如把 `StatusHistory` 的构造或 `session.add` 前的某个内部函数 patch 成 `raise RuntimeError`），然后调用 PATCH，断言：
   - 接口返回 500（或测试客户端捕获异常）；
   - 事务回滚后 `event.status` **仍等于旧值**（未变）；
   - `status_history` 行数**未增加**。
   这是最直接、最不依赖数据库行为的做法。

2. **外键违规法（软删除后仍有意义的场景）**：若未来存在"绕过应用层直接删 event"的路径，可验证外键约束生效时 `status_history` 的写入被拒。但本轮软删除后正常路径不会删 event，故此条仅作补充验证外键已开启，不作为原子性的主证。

3. **`session.rollback()` 显式验证**：在测试里手动构造一个"先改状态、再在提交前抛异常并 rollback"的最小单元，直接断言 SQLAlchemy 会话的原子语义。

主证采用**方案 1（注入失败）**：它不依赖任何数据库类型/长度的实现细节，纯靠代码桩确定性地制造"历史写入失败"，能干净地证明"状态没改 + 历史没写"这两个原子性结论。

## 3. 数据库设计

### 3.0 `event` 表新增 `deleted_at`（软删除）

在 V0.4.1 的 6 列（title/severity/description/id/created_at/status）基础上，新增第 7 列：

| 列 | 类型（DDL） | 约束 | 说明 |
|---|---|---|---|
| `deleted_at` | DATETIME | **NULL**（无默认值） | `NULL` = 未归档；非 `NULL` = 已归档，值为归档时间（UTC） |

模型层写法：

```python
# Event 模型新增：
deleted_at: datetime | None = Field(default=None, index=True)
```

- 可空、默认 `None`，对既有 3 行数据**无影响**（新列自动为 `NULL`，即"未归档"）。
- 加索引 `ix_event_deleted_at`，供未来"归档中心"按归档时间筛选。

### 3.1 `status_history` 表结构

| 列 | 类型（DDL） | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK | 自增主键 |
| `event_id` | INTEGER NOT NULL | **外键→`event.id`（启用强制）+ 索引** | 归属事件 |
| `old_status` | VARCHAR(13) NOT NULL | — | 变更前状态（三值之一） |
| `new_status` | VARCHAR(13) NOT NULL | — | 变更后状态（三值之一） |
| `reason` | VARCHAR(1000) NOT NULL | 默认 `''` | 变更/重开原因；特定转移强制非空（§5.1） |
| `action` | VARCHAR(50) NOT NULL | 默认 `'status_change'` | 动作类型（`status_change` / `archive` / `restore`，见 §5.4） |
| `actor_id` | VARCHAR(64) NOT NULL | 默认 `'local-dev'` | 操作主体（本地开发占位） |
| `changed_at` | DATETIME NOT NULL | `default_factory=now(utc)` | 变更时间戳（UTC） |

模型层写法（示意，编码阶段落地）：

```python
class StatusHistory(SQLModel, table=True):
    __tablename__ = "status_history"
    id: int | None = Field(default=None, primary_key=True)
    event_id: int = Field(foreign_key="event.id", index=True)
    old_status: str = Field(max_length=13)
    new_status: str = Field(max_length=13)
    reason: str = Field(default="", max_length=1000)
    action: str = Field(default="status_change", max_length=50)
    actor_id: str = Field(default="local-dev", max_length=64)
    changed_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
```

> 说明：`old_status`/`new_status` 用 `VARCHAR(13)` 只为与 `event.status` 的 `VARCHAR(13)` 对齐（13 = `investigating` 长度），**不依赖其长度做任何校验或失败触发**——值域由 Pydantic 枚举在 API 边界把关（见 §5.1、§5.3）。

### 3.2 迁移脚本（两个文件）

本轮有**两处**结构变更，拆成两个迁移，按依赖顺序：

**`0003_add_event_deleted_at.py`**（先做，软删除是外键强制的前置）：

```sql
ALTER TABLE event ADD COLUMN deleted_at DATETIME;
CREATE INDEX ix_event_deleted_at ON event (deleted_at);
```

- `down_revision = "0002"`；`upgrade()` 加列 + 建索引；`downgrade()` 删索引 + 删列（本机 sqlite3 3.49.1 支持原生 `DROP COLUMN`）。
- `deleted_at` 可空、无默认值，`ADD COLUMN` 对已有行直接补 `NULL`（未归档），**零数据风险**。

**`0004_add_status_history.py`**（后做，历史表引用 event）：

```sql
CREATE TABLE status_history (
    id INTEGER NOT NULL,
    event_id INTEGER NOT NULL,
    old_status VARCHAR(13) NOT NULL,
    new_status VARCHAR(13) NOT NULL,
    reason VARCHAR(1000) NOT NULL,
    action VARCHAR(50) NOT NULL,
    actor_id VARCHAR(64) NOT NULL,
    changed_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY(event_id) REFERENCES event (id)
);
CREATE INDEX ix_status_history_event_id ON status_history (event_id);
```

- `down_revision = "0003"`；`upgrade()` 建表 + 建索引；`downgrade()` **先删 `status_history` 表**（否则外键会阻止后续删 event 列，虽本轮不删 event，仍按安全顺序写）。
- 两个迁移**都不写任何数据**，对既有 3 行 event 零影响。旧事件的"第一条历史"不是迁移补的，而是未来第一次状态变更/归档时才产生（审计从有记录那一刻开始）。

### 3.3 软删除兼容策略（重点）

- **外键有效性**：软删除不动 `event` 行，`status_history.event_id` 的 `FOREIGN KEY` 引用对象**始终存在**，启用 `PRAGMA foreign_keys=ON` 后也不会出现"归档导致外键悬挂"。
- **`downgrade()` 顺序**：先删 `status_history`（`0004` 的 downgrade）→ 再删 `event.deleted_at`（`0003` 的 downgrade）。顺序颠倒会因外键报错。
- **普通列表过滤**：`GET /events` 默认追加 `WHERE event.deleted_at IS NULL`；归档事件默认不可见，但数据仍在库中，可被归档中心（未来）检索。
- **审计留存**：归档/恢复本身也写 `status_history`（`action='archive'` / `'restore'`），因此事件从创建到归档再到恢复的完整生命周期都可追溯。
- **对既有测试的影响**：`test_events.py` 的删除用例（断言 `DELETE` 后 `GET` 404）需随语义改为"归档后默认列表不可见"，但**这 16 条属于 V0.4.1 冻结基线**——本轮要么不改动它们（用新增测试覆盖软删除新语义），要么在明确获准后同步调整（见 §8）。默认策略：**不动既有 16 条**，软删除的完整语义由 `test_status_history.py` 新增用例覆盖，并在编码阶段验证"不动 16 条"是否与软删除实现兼容（若 `DELETE` 语义改变导致 16 条里的删除用例必然失败，则需你明确批准后才能改它们）。

## 4. 后端设计（API 与数据流）

### 4.0 外键启用（`app/config.py` 或 `app/main.py` 的 engine 配置）

在创建 `engine` 后挂接 `connect` 事件监听器，每次新建连接执行 `PRAGMA foreign_keys=ON`：

```python
from sqlalchemy import event as sa_event

@sa_event.listens_for(engine, "connect")
def _enable_sqlite_fk(dbapi_conn, _record):
    dbapi_conn.execute("PRAGMA foreign_keys=ON")
```

- 应用连接与 Alembic 迁移连接都走 `app.config` 里的 engine 配置来源，故**都生效**。
- 编码阶段需验证：`test_config.py` 的引擎 URL 断言、迁移测试的临时库连接，都不因此受影响。

### 4.1 现有 `PATCH /events/{event_id}` 增强（而非新增路由）

状态变更**复用现有 PATCH**，但增加三件事：

1. **状态变更检测**：比较 `payload.status`（若提交）与 `event.status`，只有**真正变化**时才写历史（status 未变 → 不产生历史行，避免噪音）。
2. **原因校验**（§5.1）+ **历史写入**（§5.4），全部在同一事务。
3. **已归档事件不可再编辑状态**（默认策略）：`event.deleted_at` 非空时，PATCH 状态变更返回 409 或 422（编码阶段定），避免"归档事件被悄悄改状态"。

数据流：

```
PATCH /events/{id} {status:..., reason:...}
  → get event (404 若无；若已归档且尝试改状态 → 拒绝)
  → 若提交了 status 且 ≠ 当前值：
        校验 reason（investigating→resolved / resolved→* 必填）
        记 old_status = 当前值
  → event.sqlmodel_update(其余字段)
  → 若状态变化：session.add(StatusHistory(...))
  → session.commit()   ← 状态与历史同事务，一次提交
  → 返回更新后的 event
```

### 4.2 新增 `GET /events/{event_id}/history`

- 返回该事件的**状态变更历史**（含归档/恢复动作，§5.4），按 `changed_at` / `id` 升序（时间线从旧到新）。
- 响应模型 `StatusHistoryRead`（只读，`from_attributes=True`）。
- **不提供** `PATCH/DELETE /status_history/...` 路由 —— 这是需求 8 "只追加、不可改"的落地方式。

### 4.3 `EventUpdate` 新增 `reason` 字段

- `reason: str | None = Field(default=None, max_length=1000)`。
- 它**不是 event 表的列**，只是 PATCH 请求里的"变更说明"载体，用于写入历史表；`model_dump(exclude_unset=True)` 时它会被单独取出，**不会**被 `sqlmodel_update` 写进 event（event 没有这个字段，需在更新逻辑里手动排除）。
- 显式 `null` 沿用既有 `reject_explicit_null` 校验（自动覆盖新字段，无需改那个校验器）。

> 这里有个易错点会在编码时处理：`reason` 混在 `payload` 里，若直接 `event.sqlmodel_update(payload.model_dump(...))` 会报"event 无 reason 字段"。设计：先 `pop` 出 `reason` 单独处理，其余字段走 `sqlmodel_update`。

### 4.4 `DELETE /events/{event_id}` 改为软删除（归档）

- 语义变更：**不删行**，把 `event.deleted_at` 设为当前 UTC 时间，并写一条 `action='archive'` 的历史记录（`old_status`/`new_status` 均记当前状态，`reason` 可为空或记"归档"）。
- 状态码：沿用 204（编码阶段确认；若需返回更新后的 event 以便前端即时刷新，可改 200 + body）。
- 归档本身与历史写入**同一事务**（§5.3 原子性同样适用）。
- 已归档事件：`get_event` 仍可读（详情/历史可见），但 `update_event` 状态变更被拒（§4.1）。
- **本轮不实现恢复接口**（评审要求"未来增加恢复操作"，见 §7 边界）；恢复接口将写 `action='restore'` 历史记录，机制已在 §5.4 预留。

## 5. 校验规则与测试设计

### 5.1 原因（reason）强制规则

| 转移方向 | reason 要求 | 返回 |
|---|---|---|
| investigating → resolved | **必填**（非空、非纯空白） | 否则 422 |
| resolved → investigating / open | **必填**（重开原因） | 否则 422 |
| 其它方向（open→investigating、investigating→open 等） | 可选（默认空串） | — |

校验函数（后端权威版，编码阶段实现）：`validate_status_transition(old, new, reason) -> None`，非法时 `raise ValueError` → FastAPI 转 422。

### 5.2 前端校验（体验层）

- 编辑弹窗里：当选"resolved"且当前是 investigating → 显示并**必填**"解决原因"输入框。
- 当从 resolved 切到其它 → 弹**二次确认弹窗** + **必填**"重开原因"。
- 与后端规则**完全一致**，但前端只拦"顺手操作"，后端才是不可绕过的闸门。

### 5.3 `tests/test_status_history.py` 用例清单

| 类别 | 用例 |
|---|---|
| 历史持久化 | 状态变更后 `GET /events/{id}/history` 返回 1 条，且 old/new/reason/action/actor_id 正确 |
| 时间线顺序 | 多次变更后按 `changed_at` 升序返回 |
| 任意方向切换 | open→investigating→resolved→open 全链路各写一条历史 |
| 无变化不写历史 | PATCH 未提交 status，或 status 等于当前值 → 历史行数不变 |
| 原因必填 | investigating→resolved 缺 reason → 422；resolved→open 缺 reason → 422 |
| 原因可选 | open→investigating 无 reason → 200，历史 reason 为 `''` |
| 非法状态 | PATCH 传非法 status → 422（既有） |
| 显式 null | status/reason 显式 null → 422（既有校验器覆盖） |
| 局部更新 | 只改 title 不改 status → 无新历史、status 不变 |
| **事务回滚（注入法）** | monkeypatch 历史写入为必然抛异常 → 断言 PATCH 报错后 event.status **未变** 且 history 行数**未增**（见决策五） |
| **事务回滚（外键违规补充）** | 验证 `PRAGMA foreign_keys=ON` 已生效：直接插入不存在的 event_id 的历史被拒（证明外键强制，非原子性主证） |
| 只追加不可改 | 直接 PATCH/DELETE `/status_history/{id}` → 404（路由不存在） |
| 详情页数据 | `GET /events/{id}/history` 对不存在 event → 404 |
| **软删除归档** | `DELETE /events/{id}` 后：`deleted_at` 非空、行仍存在、`GET /events` 默认列表不含该事件、产生 `action='archive'` 历史记录 |
| **归档不可编辑状态** | 已归档事件 PATCH 改 status → 拒绝（409/422，编码阶段定） |
| **归档可读** | 已归档事件 `GET /events/{id}` 与 `GET /events/{id}/history` 仍可读 |

### 5.4 审计完整性约束（需求 8、9、11）

- `action` 取值扩展为三类：`"status_change"`（状态切换）、`"archive"`（归档）、`"restore"`（恢复，未来）。本轮实现前两类，`"restore"` 仅在模型/常量中预留。
- `actor_id` 恒为 `"local-dev"`（集中常量 `DEFAULT_ACTOR_ID = "local-dev"`），**仅作为开发环境占位身份**，未来接入账号系统后替换为该常量来源。
- 二者**不接收客户端输入**：PATCH 请求体里即便传了 `actor_id`/`action`，也因 `extra="forbid"` 被拒（422），历史记录里的值只由后端写入。
- `changed_at` 由后端 `default_factory` 生成，客户端无法伪造时间戳。
- **归档/恢复也写审计**：`DELETE /events/{id}` 归档时写一条 `action='archive'` 历史，未来恢复时写 `action='restore'`，保证事件全生命周期可追溯。

## 7. 明确待确认 / 已知边界

1. **删除语义变更对既有 16 条测试的影响**（最重要）：`DELETE /events/{id}` 从"物理删除"改为"软删除归档"后，`test_events.py` 中"删除后 `GET` 得 404"的断言会失效。默认策略是**不动这 16 条冻结基线**，软删除新语义由 `test_status_history.py` 新增用例覆盖；但若软删除实现导致这 16 条里的删除用例必然失败，则需你**明确批准后才能修改** `test_events.py`。编码前我会先跑一次全量测试确认影响面，再决定是否需要你授权。

3. **已归档事件的编辑限制**：默认"可读、不可改状态"，状态码用 409 还是 422 待编码阶段定（不影响设计结论）。

5. **V0.4.1 真实库迁移与合并是 V0.4.2 的前置**（你已明确，保持不变）：当前真实库仍是 5 列、**无 `alembic_version` 表**、无 `status` 列，尚未执行 `stamp`/`upgrade`。V0.4.2 的 `0003`/`0004` 依赖 `0002` 已应用，因此真实库必须先完成 V0.4.1 迁移。

## 9. 为什么这样设计能保证"不丢数据、不破坏既有功能"

1. `0003`/`0004` 是**纯新增结构**（加可空列 + 新建表），不删任何列、不改任何既有数据行 —— 迁移风险趋近于零。
2. 删除升级为**软删除**，事件与历史**永远留存**，外键始终有效，彻底消除"删事件导致审计悬挂"。
3. 状态变更走**既有 PATCH**，只是"加历史 + 加校验 + 归档限制"，severity/status 独立性、局部更新、搜索筛选、统计卡片、编辑**全部原样保留**。
4. 审计"只追加"由"**不提供修改/删除历史的路由**"从架构上保证，比"靠前端藏按钮"可靠得多。
5. 事务原子性用"单 Session 单 commit"保证，回滚测试改用**确定性注入法**（不依赖 SQLite 的 VARCHAR 长度限制，后者实际不强制）。
