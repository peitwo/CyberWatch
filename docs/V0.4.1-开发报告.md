## 三、迁移 SQL（原文，未做任何修饰）

### 3.1 完整迁移 SQL `alembic upgrade head --sql`

```sql
CREATE TABLE alembic_version (
    version_num VARCHAR(32) NOT NULL,
    CONSTRAINT alembic_version_pkc PRIMARY KEY (version_num)
);
CREATE TABLE event (
    title VARCHAR(100) NOT NULL,
    severity VARCHAR(6) NOT NULL,
    description VARCHAR(1000) NOT NULL,
    id INTEGER NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (id)
);
INSERT INTO alembic_version (version_num) VALUES ('0001') RETURNING version_num;
ALTER TABLE event ADD COLUMN status VARCHAR(13) DEFAULT 'open' NOT NULL;
UPDATE alembic_version SET version_num='0002' WHERE alembic_version.version_num = '0001';
```

### 3.2 本轮增量 SQL `alembic upgrade 0001:0002 --sql`

```sql
ALTER TABLE event ADD COLUMN status VARCHAR(13) DEFAULT 'open' NOT NULL;
UPDATE alembic_version SET version_num='0002' WHERE alembic_version.version_num = '0001';
```

**这两段是本轮的重点，请对照着看：**

- 真正改动 `event` 表的语句**只有一句** `ALTER TABLE event ADD COLUMN ...`。
- 那句 `CREATE TABLE event` 属于基线 `0001`。**对已有库它不会执行**——因为你会先 `alembic stamp 0001` 认领基线，Alembic 认为 `event` 表已经建好了。
- 没有任何 `DROP` / `DELETE` / `UPDATE event` 语句。`UPDATE` 只作用于 `alembic_version` 那张记账表。
- 离线模式（`--sql`）**不连接数据库**：上面的命令跑完后，目标路径下没有生成任何 `.db` 文件（已实测确认）。这正是「先给你过目 SQL，你点头再执行」的实现方式。

用真实库的原始 DDL 建库 + 灌入真实库那 3 行数据（id 与 `created_at` 含微秒都照抄）→ `alembic stamp 0001` → `alembic upgrade head`：

## 四、数据库路径与 Alembic URL 解析（你要求先修的部分）

### 4.1 改前的真实问题

```python
DATABASE_URL = "sqlite:///./cyberwatch.db"     # 相对「进程 cwd」
```

三个连带后果：

1. 在别的目录启动服务，会在**那个目录里悄悄新建一个空库**（V0.3 时期我就是利用这一点做隔离验证的），于是出现「两个 `cyberwatch.db`」的分叉风险。
2. 一旦 Alembic 在迁移 B 目录的库，而服务在连 A 目录的库，「迁移成功」会变成假象。
3. 更隐蔽的一条：`migrations/env.py` 里的
   ```python
   config.set_main_option("sqlalchemy.url", os.environ.get("ALEMBIC_DATABASE_URL", DATABASE_URL))
   ```
   是**无条件覆盖**。测试代码先 `config.set_main_option("sqlalchemy.url", 临时库)`，`env.py` 一跑就把临时库 URL **换成了默认（真实）库 URL**。测试以为在改临时库，实际改的是真实库。**这是本轮必须修掉的第一优先级问题。**

### 4.2 修法一：把路径变成项目根绝对路径 + 支持环境变量

`app/config.py`（新增，唯一真相来源）：

```python
BASE_DIR = Path(__file__).resolve().parent.parent       # 与 cwd 无关
DATABASE_URL_ENV = "CYBERWATCH_DATABASE_URL"
DEFAULT_DATABASE_PATH = BASE_DIR / "cyberwatch.db"

def resolve_database_url(explicit: str | None = None) -> str:
    if explicit is not None and explicit.strip():
        return explicit.strip()                          # ① 调用方显式传入
    override = os.environ.get(DATABASE_URL_ENV)
    if override is not None and override.strip():
        return override.strip()                          # ② 环境变量
    return default_database_url()                        # ③ 项目根绝对路径
```

**明确的三级优先级**（高 → 低）：

| 级别 | 来源 | 用途 |
|---|---|---|
| ① | 调用方显式传入（Alembic `Config` 的 `sqlalchemy.url`） | 测试 / 程序化调用，**最高，不可被覆盖** |
| ② | 环境变量 `CYBERWATCH_DATABASE_URL` | 测试与未来部署覆盖数据库位置 |
| ③ | `<项目根>/cyberwatch.db`（绝对路径） | 默认值 |

同时 `app/main.py` 与 `migrations/env.py` **都** `from app.config import resolve_database_url`，所以「应用连的库」和「迁移改的库」在代码层面就是同一个函数算出来的，不可能分叉。

> **术语**：`explicit` 就是「调用方直接塞进来的值」。它的存在是为了解决第 3 条问题——测试把临时库 URL 塞进来后，`env.py` 只能尊重它，不许改成别的。

> **一处取舍要你知道**：设计文档里当初用的是 `ALEMBIC_DATABASE_URL`，现在统一成 `CYBERWATCH_DATABASE_URL` 一个名字。名字只有一个，就不存在「该设哪个变量」的歧义——这正是你要求的「统一解析逻辑」。

### 4.3 修法二：`env.py` 不许覆盖调用方指定的 URL

```python
# migrations/env.py
_caller_url = (config.get_main_option("sqlalchemy.url") or "").strip()
config.set_main_option(
    "sqlalchemy.url",
    resolve_database_url(explicit=_caller_url or None),   # ← 调用方给了就听调用方的
)
```

`alembic.ini` 里的 `sqlalchemy.url` **留空**，所以「调用方没给」时才会轮落到环境变量与默认值。

**测试怎么验证的**（`tests/test_migrations.py::test_env_py_respects_caller_url_and_never_falls_back_to_env_var`）：

1. 造两个临时库路径：`caller.db`（调用方指定）与 `decoy.db`（诱饵）。
2. 把环境变量 `CYBERWATCH_DATABASE_URL` 指向**诱饵**。
3. 调用方用 `Config` 显式指定 `caller.db`，执行 `upgrade head`。
4. 断言：`caller.db` 建好了表；**`decoy.db` 文件根本不存在**。

如果 `env.py` 还是旧写法，第 4 步必然失败——这条测试就是这个 bug 的哨兵。

### 4.4 测试进程如何保证「绝不连接真实库」

`tests/conftest.py` 里做了一件事，顺序是刻意安排的：

```python
TEST_TEMP_ROOT = Path(tempfile.mkdtemp(prefix="cyberwatch-tests-"))
os.environ["CYBERWATCH_DATABASE_URL"] = f"sqlite:///{(TEST_TEMP_ROOT / 'cyberwatch-test.db').as_posix()}"

# ↓↓↓ 环境变量就位之后，才允许 import app
from app.main import app, get_session
```

**为什么这样能保证安全**：pytest 收集测试模块之前，一定会先导入同目录下的 `conftest.py`。所以在任何 `from app.main import ...` 之前，环境变量已经指向系统临时目录，`app.main` 里 `engine = create_engine(DATABASE_URL, ...)` 拿到的就是临时路径。即使某天有人让测试跑起了 `lifespan`（那个只读结构检查），它查询的也是临时库。

另外三条断言把它固定下来（`tests/test_config.py`）：

- `test_app_database_url_points_into_system_tempdir`：默认引擎路径必须在系统临时目录内；
- `test_app_engine_url_points_into_system_tempdir`：引擎的 `url.database` 同上；
- `test_real_database_file_is_never_the_default_target`：真实库路径 ≠ 测试进程使用的路径。

迁移测试另有 11 条**每一条都调用** `assert_in_tempdir(db_path, in_tempdir)`：断言路径在系统临时目录内，且不等于 `<项目根>/cyberwatch.db`。

### 4.5 一个 Windows 上的真实坑（值得记住）

第一版 `alembic.ini` 我用中文写了注释，测试立刻报：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xa6 in position 36
```

原因：**Alembic 用平台默认编码读 `alembic.ini`**，中文 Windows 上是 GBK，遇到 UTF-8 的中文注释就炸。修法是把 `alembic.ini` 写成**纯 ASCII**（中文说明放到 `migrations/env.py` 的 docstring 与本报告里）。ini 文件保持 ASCII 是个通用好习惯。

顺带还修掉一个弃用告警：`path_separator = os`（Alembic 1.20 对 `prepend_sys_path` 旧的分隔方式发了 `DeprecationWarning`）。

## 五、给初学者的重点：Alembic 为什么不会丢数据

### 5.1 一句话

**因为这次迁移从头到尾只有一条 `ALTER TABLE ADD COLUMN`，没有任何语句去动那 3 行数据。**

### 5.2 先说会丢数据的三种做法（反例）

| 反例 | 为什么丢数据 |
|---|---|
| 删掉 `cyberwatch.db` 让 `create_all` 重建 | 3 行数据**全部消失**，且不可恢复 |
| `CREATE TABLE event_new AS SELECT ...` 手工搬列 | 漏写一列就丢一列；中途失败还可能留下半成品 |
| `batch_alter_table` 重建整张表 | SQLite 会走「建新表 → 复制 → 删旧表 → 改名」12 步；本身能保数据，但步骤多、失败面大，**本次并不需要** |

### 5.3 本方案实际发生了什么（逐步）

1. **`ADD COLUMN` 是「改结构定义」，不是「搬数据」。** SQLite 只改 `sqlite_master` 里的建表语句文本，**不触碰数据页**。3 行数据待在原处，一个字节都没被移动。
2. **`DEFAULT 'open'` 让旧行「自动」有了值。** 新列是 `NOT NULL`，SQLite 就强制要求你给一个非 NULL 的常量默认值——加列的**同一瞬间**，旧行读出来就是 `open`。**不需要 `UPDATE`，不需要逐行回填。** 这也解释了为什么模型上必须写 `server_default`：

   | 写法 | `create_all` 生成的 DDL | 裸 SQL 只插 id |
   |---|---|---|
   | `status: Status = Status.open` | `status VARCHAR(13) NOT NULL` | ❌ `NOT NULL constraint failed` |
   | `Field(default=Status.open, sa_column_kwargs={"server_default": "open"})` | `status VARCHAR(13) DEFAULT 'open' NOT NULL` | ✅ 自动填 `open` |

   （这是第一阶段用对照实验实测出来的，不是推测。）
3. **零 `DROP` / 零 `DELETE`。** `upgrade` 路径上没有任何删除类语句。
4. **`id` 与 `created_at` 不被触碰。** Alembic 只改结构、不写业务数据；主键值不重排，`created_at` 原样保留（测试逐行比对，连微秒都对）。
5. **`alembic_version` 表负责记账。** 它记录「当前升级到哪个版本」，所以不会重复执行、也不会漏执行——这正是 `create_all` 回答不了的「这库到底升到哪一步了」。
6. **可以离线预演。** `alembic upgrade head --sql` 只打印 SQL、不连库。先看 SQL，再决定执行——直接对应你的安全约束「禁止未经确认的迁移」。
7. **兜底是备份。** 动真实库前先整份复制到 `D:\cursor\item\CyberWatch V0.1\backups\`（在 git 仓之外、`.gitignore` 之外）。

### 5.4 一个必须如实说明的技术前提：SQLite 的 DDL 事务性

你的安全约束里写了「不假设 SQLite DDL 在所有情况下都能完整事务回滚」——这个判断是对的，而且 Alembic 自己也在日志里承认：

```
INFO  [alembic.runtime.migration] Context impl SQLiteImpl.
INFO  [alembic.runtime.migration] Will assume non-transactional DDL.
```

意思是：Alembic 在 SQLite 上**不假设 DDL 会被事务保护**（`pysqlite` 驱动不会为 DDL 隐式开事务）。所以：

- **不能假设**「迁移失败会自动回滚到原样」；
- 本次迁移只有**一条** DDL，不存在「改了一半」的中间态（要么加上了，要么没加上）；
- 真正的安全网是**迁移前的文件备份**，以及迁移前后各做一次数据比对。恢复步骤见第七节。

这也是为什么我把 `downgrade` 也写全并测过——需要回退时不用手写 SQL。

### 5.5 两个迁移脚本

`0001_baseline_event_table.py` —— 把**当前**已有的表结构写成基线（`down_revision = None`）。对已有库，它靠 `stamp` 跳过。

`0002_add_event_status.py` —— 唯一的真实变更：

```python
def upgrade() -> None:
    op.add_column("event", sa.Column("status", sa.VARCHAR(length=13),
                                     nullable=False, server_default="open"))

def downgrade() -> None:
    op.drop_column("event", "status")     # 本机 sqlite3 3.49.1 支持原生 DROP COLUMN
```

**为什么 `VARCHAR(13)`**：SQLAlchemy 给 `str, Enum` 生成的列长度 = 最长枚举值长度。`investigating` 是 13 个字符，所以是 13（现有 `Severity` 最长是 `medium`，所以现库是 `VARCHAR(6)`，规律一致）。迁移脚本里必须写一样的长度，否则「迁移建出的表」和「`create_all` 建出的表」会不一致。

**为什么手写不用 `--autogenerate`**：`--autogenerate` 的工作方式是「拿模型去对比数据库现状」。而这个库**没有 `alembic_version` 表**，Alembic 会以为它是全新库，于是试图 `create_table("event")`——表其实已经存在，直接报 `table event already exists`。必须先有基线、先 `stamp`，autogenerate 才有意义。手写这两条对初学者也更好：你完全掌控会生成什么 SQL。

```
GET /events → events 数组（每个元素含 status）
   → render() 遍历 COLUMNS（6 个渲染器，按声明顺序）
   → 第 4 个渲染器标了 badge:true，产出 {pill:'pill status-open', text:'待处理'}
   → 建 <span class="pill status-open">，文本走 textContent
   → 追加「操作」列（第 7 列）
```

`COLUMNS` 是**表格列的唯一声明处**：列顺序、列数量、哪一列是徽章都只在这里定义。`colSpan` 用 `COLUMNS.length + 1` **自动推导**，所以「加了列忘了改 colspan」这个坑从此不会再出现（V0.3 那个靠 `value===e.severity` 猜列的脆弱写法也一并修掉了——原来只要某条事件标题恰好等于 `high`，那一列就会被误渲染成徽章）。

### 6.2 状态筛选（前端本地 + 后端 API 双通道）

前端：`render()` 里的过滤条件三项并存（**AND**）：

```js
const filtered = events.filter(e =>
  (level === 'all' || e.severity === level) &&
  (state === 'all' || e.status === state) &&
  (`${e.title} ${e.description ?? ''}`).toLowerCase().includes(term));
```

后端：`GET /events?status=investigating`（与 `?severity=` 可同时使用）：

```python
statement = select(Event)
if severity: statement = statement.where(Event.severity == severity)
if status:   statement = statement.where(Event.status   == status)
statement = statement.order_by(Event.id.desc()).offset(offset).limit(limit)
```

两者都验证过：真实 Chrome 里「等级=中风险 + 状态=调查中」命中 1 行；API 上 `?severity=high&status=open` 命中 1 条（若还是旧写法会命中全部 open 的）。

### 6.3 编辑状态

```
点「编辑」→ openEditDialog(id) 从已加载的 events 里取出记录
          → 预填 title / severity / status / description
          → 提交时 payload = {title, severity, status, description}
          → PATCH /events/{id}
          → 后端 EventUpdate 校验（三道门，见 6.5）
          → event.sqlmodel_update(payload.model_dump(exclude_unset=True))
          → commit / refresh
          → 返回 EventRead（含 status）
          → 前端关闭弹窗 → loadEvents()（列表 + 4 张统计卡片一起刷新）→ 顶部绿色提示条
```

**只发这四个字段**是刻意的：`exclude_unset=True` 只导出「请求体里真正出现过的字段」，所以未提交的字段保持原值。已在真实浏览器里抓到请求体核对：

```
PATCH http://127.0.0.1:8788/events/3
      {"title":"Routine Patch Applied","severity":"low","status":"resolved","description":"例行补丁已上线"}
```

### 6.4 新建 / 删除（本轮只做增量，不动原有链路）

- 新建：弹窗仍然**只提交 3 个字段**，`status` 由后端 `default=Status.open` 补上（需求 2）。真实浏览器里新建一条后核对返回 `status == "open"`。
- 删除：仍是「先弹确认框 → 用户确认 → `DELETE /events/{id}` → 刷新列表 + 统计卡片」，本轮未改动，回归验证仍通过。
- 统计卡片：`loadEvents()` 里按 `severity` 统计，本轮未改（需求 9 要求保留）。**注意**：状态筛选是纯前端过滤，卡片数字对应的是「本次加载的全部记录」，不随筛选变化——这与 V0.3 的行为一致。

### 6.5 后端三道校验门（`status` 自动获得全部防护）

| 门 | 规则 | 违规 |
|---|---|---|
| ① 字段名 | `EventCreate` / `EventUpdate` 的 `extra="forbid"` | `{"statu": "resolved"}` → **422** |
| ② 显式 null | `reject_explicit_null`（**既有 before 校验器，本次一个字没改**） | `{"status": null}` → **422** |
| ③ 取值范围 | `Status` 是 `str, Enum` 三选一 | `"closed"` / `"OPEN"` / `""` / `123` / `true` → **422** |

第 ② 条之所以「零改动」就生效：那个校验器遍历的是**整个提交体**，不枚举字段名——

```python
null_fields = [name for name, value in data.items() if value is None]
```

所以加任何新字段都自动获得 null 防护。这是「写通用校验」而不是「逐字段写 if」的收益。

### 8.2 逐处说明

**`app/config.py`（新增，全文 47 行，建议整份读）**
- `BASE_DIR = Path(__file__).resolve().parent.parent`：基于 `__file__`，**与 cwd 无关**。`main.py` 的 `templates` / `static` 也用它。记住「凡是要定位文件，都用 `__file__` 推，不要用 `./`」。
- `sqlite_file_path()`：把 `sqlite:///xxx` 拆出文件路径。它的用处是让 `ensure_schema_ready()` 能**先判断文件在不在**，避免「连接动作顺手创建一个空库」。

**`app/main.py` 的 `Status` 与 `status` 字段**

```python
class Status(str, Enum):
    open = "open"
    investigating = "investigating"
    resolved = "resolved"

status: Status = Field(default=Status.open, sa_column_kwargs={"server_default": "open"})
```
- `default` → 应用侧默认值（新建事件默认 open）。
- `server_default` → **数据库侧**默认值（迁移时给旧行补 open；也是 SQLite 允许 `ADD COLUMN ... NOT NULL` 的前提）。

**`app/main.py::ensure_schema_ready()`（新增）**

db_file = sqlite_file_path(DATABASE_URL)
