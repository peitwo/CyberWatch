### 1.4 `DATABASE_URL` 的解析方式（你要求先确认的点）

```python
DATABASE_URL = "sqlite:///./cyberwatch.db"
```

- `sqlite:///` 后面跟的是**文件路径**，`./` 表示**相对当前工作目录（cwd）**，不是相对代码仓。
- SQLAlchemy 把它交给 SQLite 打开时，用的是进程启动瞬间的 cwd。
- 后果：`cd cyberwatch-starter && uvicorn app.main:app` 用的是 `cyberwatch-starter/cyberwatch.db`；换成 `cd /tmp/x && uvicorn app.main:app`，程序会在 `/tmp/x/` 里**悄悄新建一个空库**，而 `templates` / `static` 因为走 `BASE_DIR`（基于 `__file__`）依然正常。V0.3 的真机验证正是利用这一点做隔离。
- 对 Alembic 的直接影响：**如果 `alembic.ini` 里自己写一份 URL，就会出现"app 连 A 库、alembic 迁移 B 库"的分叉**。所以本方案让 Alembic 复用同一个 `DATABASE_URL` 常量（单一真相来源），见 4.3。
- 附带风险：`alembic` 命令也必须在 `cyberwatch-starter` 目录下执行，否则迁移的是别的目录下的库。README 会写明。

> 可选改进（本轮**不做**，避免改变既有行为）：把 URL 改成 `sqlite:///{(BASE_DIR / 'cyberwatch.db').as_posix()}`，彻底消除 cwd 依赖。代价是 V0.3 那套"临时 cwd 隔离验证"的技巧失效。

## 二、数据库设计

### 2.1 字段定义

```python
class Status(str, Enum):
    open = "open"
    investigating = "investigating"
    resolved = "resolved"


class EventBase(SQLModel):
    title: str = Field(min_length=3, max_length=100)
    severity: Severity = Severity.low
    status: Status = Field(default=Status.open, sa_column_kwargs={"server_default": "open"})
    description: str = Field(default="", max_length=1000)
```

### 2.2 实测出来的确切 DDL（探针输出，非推测）

```
status VARCHAR(13) DEFAULT 'open' NOT NULL
```

- **`VARCHAR(13)`**：SQLAlchemy 对 `str, Enum` 生成的枚举列，长度取**最长枚举值**的长度。`investigating` 是 13 个字符，所以是 13（现有 `Severity` 的最长值是 `medium`，所以现在的库是 `VARCHAR(6)`，完全对应）。迁移脚本里必须写同一个长度，否则"迁移出来的表"和"create_all 建出来的表"会不一致。
- **`DEFAULT 'open'`**：这是 `server_default` 的效果，也是 SQLite 允许 `ADD COLUMN ... NOT NULL` 的**前提**。
- **`NOT NULL`**：库里不允许出现 NULL 状态。

### 2.3 为什么不加 CHECK 约束

- 现有 `severity` 列**没有** CHECK，值域由 Pydantic 把关（Pydantic 层已经是 422，DB 层不重复设防）。
- 加 CHECK 会让**将来任何一个新状态的加入**都必须再做一次迁移，而 SQLite 改约束需要重建整张表（`batch_alter_table` 12 步流程），风险远大于收益。
- 代价（必须知道）：**绕过 API 直接用 SQL 写入非法状态，数据库不会拦**。这是与现有设计一致的取舍。测试里会有一条断言把"值域把控在 Pydantic"这件事显式固化下来。

### 2.4 默认值：为什么模型上要写 `server_default`

探针给了对照证据：两个只差 `server_default` 的模型，用裸 SQL 只插 `id` 时——没有 `server_default` 的那个**直接抛 `NOT NULL constraint failed`**。

| 写法 | create_all 生成的 DDL | 裸 SQL `INSERT INTO event(id) VALUES(1)` |
|---|---|---|
| `status: Status = Status.open` | `status VARCHAR(13) NOT NULL` | ❌ IntegrityError |
| `status: Status = Field(default=..., sa_column_kwargs={"server_default":"open"})` | `status VARCHAR(13) DEFAULT 'open' NOT NULL` | ✅ 自动填 `open` |

意义有两层：

1. **Python 侧** `default=Status.open` 负责"应用建的新事件默认 open"（需求 2）。
2. **数据库侧** `server_default='open'` 负责"迁移时给已有行补上 open"（需求 7），并且让 `create_all` 建出的表与 Alembic 迁移出的表**完全一致**（这点会被第 3 条迁移测试验证），避免两套建表路径长期漂移。

### 2.5 索引与表结构

- **不建索引**：学习项目数据量 ≤ 100 条，`WHERE status = ?` 全表扫描完全无感；建索引反而让迁移多一条语句、多一个失败点。
- **不改其它列、不改主键、不动 `created_at`**。
- **物理列顺序会变**：`ADD COLUMN` 只能追加到**末尾**，所以迁移后库里是 `title, severity, description, id, created_at, status`，而 `create_all` 按类内声明顺序建。这对 SQLAlchemy/SQLModel **完全无害**（按列名取值），但如果有人用 `SELECT *` 再按位置下标取值就会错位。**结论：结构比对测试必须按列名比对，不能按位置比对。**

## 三、字段校验设计（需求 5、6）

### 3.1 三层把关

| 层 | 规则 | 违规结果 |
|---|---|---|
| ① 字段名 | `extra="forbid"`（`EventCreate` / `EventUpdate` 已有） | 拼错 `statu` → **422** |
| ② 显式 null | `reject_explicit_null`（已有 before 校验器，**通用实现，无需改动**） | `{"status": null}` → **422** |
| ③ 取值域 | `Status` 是 `str, Enum` 三选一 | `"closed"` / `"OPEN"` / `""` / `123` → **422** |

**这是本方案最省事的一处**：第 ②③ 条**一行代码都不用加**。

- 第 ② 条：现有校验器是这么写的——`null_fields = [name for name, value in data.items() if value is None]`，它遍历**整个提交体**，不枚举字段名。所以只要给 `EventUpdate` 加一个 `status` 字段，`{"status": null}` 就自动被拦成 422。
- 第 ③ 条：`str, Enum` 的成员名构造出的是**大小写敏感的精确匹配**，FastAPI 遇到非法枚举值自动产出 422 校验错误体。

### 3.2 `EventUpdate` 的形状

```python
class EventUpdate(SQLModel):
    model_config = ConfigDict(extra="forbid")

    title: str | None = Field(default=None, min_length=3, max_length=100)
    severity: Severity | None = None
    status: Status | None = None          # ← 唯一新增行
    description: str | None = Field(default=None, max_length=1000)

    @model_validator(mode="before")
    @classmethod
    def reject_explicit_null(cls, data):   # ← 一个字都不改
        ...
```

类型必须是 `Status | None = None`，不能写成 `Status = Status.open`：后者会让"没提交 status"被 Pydantic 填成 `open` 并进入 `exclude_unset` 的候选集合吗？不会（`default` 不属于"被显式设置"），但会让"未提交"和"提交了 open"两个语义在代码里失去区分度，也会让类型标注撒谎。用 `| None = None` 与现有三个字段保持同构。

### 3.3 局部更新语义（需求 5）

`update_event` 现有实现：

```python
event.sqlmodel_update(payload.model_dump(exclude_unset=True))
```

- `exclude_unset=True` 只导出**请求体里真正出现过的字段**。PATCH `{"status": "investigating"}` → 导出 `{"status": ...}` → 只 UPDATE 这一列。
- 这是"未提交字段保持原值"的**全部实现**。危险点：把它改成 `model_dump()`，未提交字段会以 `None` 进入更新集合，NOT NULL 列立刻 500。**报告里会专门标注这个易被后人破坏的位置**。

### 3.4 severity 与 status 的独立性（需求 4）

- 两者是同一个表里两个**互不相干的列**，没有任何联动代码。
- 校验器只拦 null，不做"高等级必须处于某状态"之类的联动。**没有任何地方会因为改 status 而写 severity。**
- 测试用**双向**断言固化：改 status 后 severity 不变；改 severity 后 status 不变。

### 3.5 状态之间自由切换，不做状态机（需求 3）

明确**不实现**任何状态流转限制：

```
open ⇄ investigating ⇄ resolved      # 三个方向都可逆，含 resolved → open
```

- 编辑弹窗的 `<select>` 三个选项全部始终可选，不置灰、不禁用。
- 后端不校验"上一个状态是什么"。
- 这是刻意取舍：需求 3 原文就是"允许在任意三个有效状态之间切换，包括 resolved 重新改回 investigating 或 open"。若未来要加"已解决不能直接回到 open"这类规则，应该引入独立的状态机模块，而不是把它藏进校验器。

### 4.3 `env.py` 的 URL 注入

```python
import os, sys
from pathlib import Path

from sqlalchemy import engine_from_config, pool
from sqlmodel import SQLModel

```

三个设计点：

1. **`sys.path.insert(BASE_DIR)`**：`alembic.ini` 里的 `prepend_sys_path = .` 是**相对 cwd** 的，从别的目录运行命令就会 import 失败。这与 V0.3 里 `BASE_DIR` 基于 `__file__` 的教训是同一类问题，用代码固定住。
2. **`from app.main import DATABASE_URL`**：import 时模块级会执行 `create_engine(...)`，但 SQLAlchemy 引擎是**惰性**的，不连接、不建文件、不碰任何数据，安全。
3. **`ALEMBIC_DATABASE_URL` 环境变量覆盖**：这是"在独立临时库上测迁移"（需求 12）的机制。测试时把它指向 `%TEMP%` 下的临时文件，真实库完全不在场。

`target_metadata = SQLModel.metadata` 用于将来 `--autogenerate`；`app.main` 被 import 后模型都已注册进 metadata。

### 4.4 两个迁移脚本

**`0001_baseline_event_table.py`** —— 把**当前**已有的表结构写成基线：

```python
revision = "0001"
down_revision = None

def upgrade() -> None:
    op.create_table(
        "event",
        sa.Column("title", sa.VARCHAR(length=100), nullable=False),
        sa.Column("severity", sa.VARCHAR(length=6), nullable=False),
        sa.Column("description", sa.VARCHAR(length=1000), nullable=False),
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("created_at", sa.DateTime(), nullable=False),
        sa.PrimaryKeyConstraint("id"),
    )

def downgrade() -> None:
    op.drop_table("event")
```

**`0002_add_event_status.py`** —— 本轮唯一的真正变更，**一条 `ADD COLUMN`**：

```python
revision = "0002"
down_revision = "0001"

def upgrade() -> None:
    op.add_column(
        "event",
        sa.Column("status", sa.VARCHAR(length=13), nullable=False, server_default="open"),
    )

def downgrade() -> None:
    op.drop_column("event", "status")
```

- `upgrade` 生成的 SQL 就是：`ALTER TABLE event ADD COLUMN status VARCHAR(13) DEFAULT 'open' NOT NULL`
- `downgrade` 用原生 `DROP COLUMN`。本机 SQLite 3.49.1 已确认支持（需 ≥ 3.35）。若将来部署到更老的 SQLite，改成 `with op.batch_alter_table("event") as batch: batch.drop_column("status")` 即可（batch 模式会重建表并复制数据，代价更高）。

**为什么这两个脚本手写，而不是 `--autogenerate`？**
`--autogenerate` 的工作方式是"拿模型定义去对比数据库现状"。而这个库**没有 `alembic_version` 表**，Alembic 会以为自己是全新库，于是试图 `create_table("event")` —— 而表其实已经存在，直接报 `table event already exists`。必须先有基线、先 `stamp`，autogenerate 才有意义。对初学者，手写这两条能完全掌控生成什么 SQL，也更适合拿来学。

### 4.5 Alembic 是怎样避免丢失已有数据的（重点）

这是你特别要求解释的部分。结论：**因为这次迁移从头到尾只有一条 `ALTER TABLE ADD COLUMN`，没有任何一条语句会移动或删除数据。**

**先说会丢数据的三种做法（反例）：**

| 反例 | 为什么丢数据 |
|---|---|
| 删掉 `cyberwatch.db`，让 `create_all` 重建 | 3 行真实数据**全部消失**，且不可恢复 |
| `CREATE TABLE event_new AS SELECT ...` 手工搬列 | 只要漏写一列就丢一列；中途失败还可能留下半成品 |
| 用 `batch_alter_table` 重建表 | SQLite 会走"建新表 → 复制 → 删旧表 → 改名"12 步；本身能保数据，但步骤多、失败面大，**本次并不需要** |

**再看本方案实际发生了什么：**

1. **`ADD COLUMN` 是元数据操作。** SQLite 的 `ALTER TABLE ... ADD COLUMN` 只改 schema 定义（表结构描述），**不触碰已有的数据页**。3 行数据待在原处，一个字节都没被搬动。
2. **`DEFAULT 'open'` 让旧行"自动"有了值。** 因为新列是 `NOT NULL`，SQLite 强制要求给出非 NULL 常量默认值；加列的同一瞬间，SQLite 就把这个默认值逻辑上应用到所有已有行。**不需要 `UPDATE` 语句，不需要逐行回填**，旧行读出来就是 `open`。
3. **零 `DROP` / 零 `DELETE`。** 两个迁移脚本里只有 `create_table`（基线，对已有库不执行）、`add_column`、以及仅用于回退的 `drop_column`。`upgrade` 路径上**没有任何删除类语句**。
4. **`id` 与 `created_at` 不被触碰。** Alembic 只改结构、不写数据；主键值不重排，`created_at` 原样保留（测试会逐行逐字段比对，连微秒都对）。
5. **Alembic 用 `alembic_version` 表记账。** 它新建一张只有一行的表记录"当前处于哪个版本"，所以不会重复执行、也不会漏执行 —— 这解决了 `create_all` 无法回答的"这个库到底升级到哪一步了"。
6. **迁移前可先离线预演。** `alembic upgrade head --sql` 以离线模式**只打印 SQL、不连数据库**。你可以在真正执行前先把这条 `ALTER TABLE` 看清楚——这正好呼应你的安全约束"禁止未经确认的迁移"：**先出 SQL，你点头，再执行**。
7. **兜底：执行前先备份。** 即便前 6 条都成立，仍然在动真实库之前把它整份复制到 `D:\cursor\item\CyberWatch V0.1\backups\cyberwatch-<时间戳>.db`（在 git 仓之外，不会被跟踪）。万一有任何意外，回滚就是覆盖回去。

**一句话总结**：Alembic 不是"更聪明的重建表"，而是"只发一条加列语句 + 用一张版本表记账"。数据之所以安全，是因为**根本没有语句去动那些数据**。

### 4.6 `lifespan` 里的 `create_all` 必须处理（关键决策）

现在的 `app/main.py:83-86`：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    SQLModel.metadata.create_all(engine)
    yield
```

`create_all` 的行为是"**只建不存在的表**"。表已存在时它什么都不做——所以对已有库，**它永远加不上 `status` 列**。一旦模型里有了 `status` 而库里没有，应用一查询就会报 `no such column: event.status`。这正是 `README.md` 里那句"SQLite `create_all()` cannot perform schema migration on existing tables"的含义，也是本轮必须引入 Alembic 的原因。

三种处理方式：

| 方案 | 行为 | 评价 |
|---|---|---|
| A. 删掉 `create_all`，启动时**只做只读结构检查** | 库里缺 `status` 列就抛出并提示"请先运行 `alembic upgrade head`" | ✅ **推荐**。单一真相来源；启动**绝不修改数据库**，最贴合你的安全约束 |
| B. 删掉 `create_all`，启动时自动 `alembic upgrade head` | 启动即把库升到最新 | 开发期省心，但"启动服务"等于自动改库结构，与"迁移需先确认"的约束精神冲突 |
| C. 保留 `create_all` | 新库建表、旧库不管 | ❌ 与 Alembic 形成双轨：`create_all` 建出的表**不会写 `alembic_version`**，之后 `upgrade` 会因为"表已存在"失败，制造最难查的不一致 |

**本方案选 A**，启动检查只读，参考实现：

```python
def ensure_schema_ready() -> None:
    with engine.connect() as connection:
        columns = {row[1] for row in connection.exec_driver_sql("PRAGMA table_info(event)")}
    if columns and "status" not in columns:
        raise RuntimeError(
            "数据库结构不是最新（event 表缺少 status 列）。"
            "请先在 cyberwatch-starter 目录执行：alembic upgrade head"
        )
```

（`columns` 为空表示库是全新的，此时同样提示先跑 `upgrade head`。这条检查是纯 `PRAGMA` 查询，**不写任何数据**。）

### 4.7 真实库的一次性迁移流程（**等你确认后才执行，本阶段不执行**）

### 4.8 SQLite + Alembic 的注意事项

| 事项 | 结论 |
|---|---|
| 需要 `render_as_batch=True` 吗 | **不需要**。只有 `ALTER COLUMN` / 加约束 / 删列才需要；本次是 `ADD COLUMN`，SQLite 原生支持 |
| 事务性 | SQLite 的 DDL 支持事务，Alembic 的 `upgrade` 是原子的：中途失败会整体回滚 |
| `connect_args={"check_same_thread": False}` | `env.py` 不需要，那是给 FastAPI 多线程用的 |
| Windows 路径 | 测试里注入 URL 用 `Path(...).as_posix()`，避免反斜杠；路径中不要出现 `%`（configparser 会做插值） |
| 迁移脚本与模型的一致性 | 靠 `tests/test_migrations.py` 的结构比对测试守住（见 7.2 第 3 条） |

## 五、后端接口设计

### 5.1 `list_events` 的筛选重构（现有一个必须修的坑）

现在的写法：

```python
statement = select(Event).order_by(...).offset(offset).limit(limit)
if severity:
    statement = select(Event).where(Event.severity == severity).order_by(...)...   # 整个重建
```

一旦照抄一行 `if status: statement = select(Event).where(...)`，**两个筛选同时使用时，后一个会覆盖前一个**（`severity` 分支被丢弃）。

改为链式追加：

```python
@app.get("/events", response_model=list[EventRead])
def list_events(session: SessionDep,
                severity: Severity | None = None,
                status: Status | None = None,
                offset: int = Query(default=0, ge=0),
                limit: int = Query(default=20, ge=1, le=100)):
    statement = select(Event)
    if severity:
        statement = statement.where(Event.severity == severity)
    if status:
        statement = statement.where(Event.status == status)
    statement = statement.order_by(Event.id.desc()).offset(offset).limit(limit)
    return session.exec(statement).all()
```

- `select(...).where(...)` 返回新的 `Select` 对象，可反复追加，条件之间自动是 `AND`。
- 非法 `?status=closed` 由 FastAPI 的枚举校验直接返回 422，无需额外代码。
- 排序 / 分页 / 默认值语义与现状完全一致（降级风险为零）。

### 5.2 `response_model` 自动带上 status

`EventRead(EventBase)` 继承 `EventBase`，`status` 加在 `EventBase` 上就意味着 `GET /events`、`GET /events/{id}`、`POST`、`PATCH` 的响应里**自动**都有 `status`。无需改任何路由的返回声明。

### 5.3 需求 14 的风险评估（现有 16 项会不会被打破）

逐个核对 `tests/test_events.py` 后判断：**不会**。唯一有比对全量响应体的用例是 `test_update_empty_payload_keeps_record`（`response.json() == original`），两侧都是接口返回、都会带 `status`，仍然相等。其余用例只断言个别字段或状态码。

风险仍在，所以第二阶段会**先跑一遍现有 16 项**再动任何代码，拿到基线后逐阶段复跑。

### 7.4 迁移测试如何保证不误伤真实库

三条同时成立才安全：
